# Editors (ACP)

`rey30-idvj acp` serves Rey30 IDvj Agent over the [Agent Client Protocol](https://agentclientprotocol.com)
(ACP), a JSON-RPC protocol that editors use to run coding agents. Once an editor is pointed at
`rey30-idvj acp`, you can pick Rey30 IDvj in its agent panel, send prompts, and watch the answer, reasoning,
tool calls and plan stream in. The agent still uses Rey30 IDvj's own providers, tools and permissions.

<Callout type="warning">
`rey30-idvj acp` is **experimental**. It's off by default, hidden from `rey30-idvj --help`, and may change
between releases.
</Callout>

## Turn it on

Pick one of these. The environment variable takes precedence over the config file, so
`REY30_EXPERIMENTAL_ACP=0` turns it off again:

```bash
export REY30_EXPERIMENTAL_ACP=1          # per process
```

```toml
# ~/.rey30-idvj/config.toml                    # every process
[experimental]
acp = true
```

If you run `rey30-idvj acp` without turning it on, it prints how to enable it and exits with status 2.
It writes nothing to stdout.

Rey30 IDvj needs a working provider before any editor can use it. Run `rey30-idvj login`, or
`rey30-idvj config set --provider <name> --api-key <key> --base-url <url> --model <id>`. The model is
resolved the same way as in the TUI: `agent.toml`, then `default_model` in `~/.rey30-idvj/config.toml`.

## Zed

Add Rey30 IDvj under `agent_servers` in Zed's `settings.json`:

```json
{
  "agent_servers": {
    "Rey30-IDvj": {
      "type": "custom",
      "command": "rey30-idvj",
      "args": ["acp"],
      "env": { "REY30_EXPERIMENTAL_ACP": "1" }
    }
  }
}
```

Open the agent panel, start a new thread and choose **Rey30 IDvj**. To see the raw traffic, run
`dev: open acp logs`.

## JetBrains

In **AI Chat**, open the menu and choose **Add Custom Agent**. This opens `~/.jetbrains/acp.json`.
Add Rey30 IDvj there. Use the absolute path to the binary:

```json
{
  "agent_servers": {
    "Rey30-IDvj": {
      "command": "/absolute/path/to/rey30-idvj",
      "args": ["acp"],
      "env": { "REY30_EXPERIMENTAL_ACP": "1" }
    }
  }
}
```

## What is supported

Rey30 IDvj speaks stable ACP protocol version **1**. It doesn't enable any draft or unstable features.

| ACP | Rey30 IDvj |
| --- | --- |
| `initialize` | Advertises `loadSession`, image and embedded-context prompts. Nothing else is advertised. |
| `authenticate` | Checks that a provider is configured. Clients that can run a terminal get a sign-in method that runs `rey30-idvj acp --login`. |
| `session/new` | Opens a session in `cwd`, which must be absolute. The session id is a Rey30 IDvj thread id. MCP servers the editor passes over stdio are connected as well as the project's own. |
| `session/load` | Replays a saved thread, including ones started in the TUI or with `rey30-idvj cli agent run`, then replies. Refused while that session has a prompt running. |
| `session/prompt` | Runs one turn. The reply's `stopReason` is `end_turn`, `max_tokens`, `max_turn_requests` (the session's cost ceiling was reached), `refusal` or `cancelled`. If the run fails, the error is shown in the reply text and the turn ends with `end_turn`. |
| `session/cancel` | Stops the turn. A tool call waiting for your permission never runs. The work done before the cancel is kept, so the next prompt continues from it. |
| `session/request_permission` | Sent for every gated tool call. You get **Allow**, **Always allow** where Rey30 IDvj offers it, and **Reject**. |

The session id is the thread id, so `rey30-idvj --resume <id>` in the terminal opens a conversation that
you started in the editor.

How Rey30 IDvj's events appear in the editor:

| Rey30 IDvj | ACP `session/update` |
| --- | --- |
| Answer text / reasoning | `agent_message_chunk` / `agent_thought_chunk` |
| Tool call starts, runs, streams output, ends | `tool_call` then `tool_call_update` (`pending`, `in_progress`, `completed`, `failed`) |
| The `todo` list | `plan` |
| Token usage for a turn | `usage_update` |

These have no standard ACP update, so they are left out rather than sent through a made-up
extension: subagent progress (a subagent's permission prompts still reach you), notices,
compaction and retry status, and background monitors. The `ask` tool isn't offered in an ACP
session.

## Permissions

An ACP session always asks before writes, shell commands and MCP tool calls. It's never
auto-approved. It uses the same tool gate and project rules (`[tools]` in `agent.toml`) as the TUI.
If you reject a call, or cancel the prompt, the call is refused just as it would be in the terminal.
**Always allow** covers that tool for the rest of the session.

## Not yet supported

- Rey30 IDvj uses its own filesystem and shell tools. It doesn't read the editor's unsaved buffers or run
  commands in the editor's terminal, so `fs/*` and `terminal/*` are never requested.
- Editor MCP servers over HTTP or SSE are skipped. Only stdio servers are connected, alongside the
  servers set up for the project (see [MCP](/docs/agent/mcp)).
- There's no `session/set_mode` yet, so plan mode and model switching aren't available from the
  editor.
